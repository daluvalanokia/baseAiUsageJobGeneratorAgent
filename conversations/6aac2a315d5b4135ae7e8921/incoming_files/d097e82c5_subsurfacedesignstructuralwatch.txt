StructureWatch Guard
Building Structure Geometry & Change-Monitoring Enhancement

ASP.NET Core / C# MVC • SQL Server spatial schema • Standalone scheduled daemon • Map + satellite/elevation evidence

Prepared from the current StructureWatch Guard interface and the supplied SatViewGuard/StructureWatch applications.
Existing references: https://aisstructureguardwatch.ai.studio  |  https://satviewguard.base44.app

1. Enhancement objective

Add a persistent building-structure inventory and geometry-baseline subsystem to StructureWatch Guard. The subsystem identifies structures above a configurable height threshold (default 100 m), stores a city/structure/vertex hierarchy, maintains an immutable original geometry baseline and a separately versioned updated geometry, and periodically compares the two. Detected coordinate movement is classified for re-validation rather than being treated automatically as structural failure.

2. Important measurement rule

Map footprints and ordinary satellite imagery should be treated as geospatial evidence, not as guaranteed millimetre-level structural measurements. The comparison engine must store source accuracy, capture time, CRS and confidence. A small coordinate difference should only become a physical millimetre/centimetre movement alert when the underlying source accuracy and processing method support that precision. For high-precision validation, route the structure to a manual 360° review or an engineering survey source such as GNSS, total station, terrestrial LiDAR or an appropriately accurate monitoring system.

3. Functional architecture

Web UI: City → Structures → Structure Detail → Vertex Geometry → Change History → Validation Queue.

MVC API layer: controllers expose city, structure, vertex, comparison and validation operations.

Application services: structure discovery, geometry normalization, source ingestion, coordinate comparison, alert classification and audit logging.

Background daemon: standalone .NET Worker Service executable; invoked continuously, by Windows Task Scheduler, systemd timer, cron, Kubernetes CronJob, or another scheduler.

Data layer: SQL Server with geography/geometry spatial types; Entity Framework Core; optional spatial indexes.

External adapters: OpenStreetMap/Overpass for mapped footprints and node geometry; authoritative city/building-department feeds where available; satellite/imagery provider; elevation/LiDAR provider.

Evidence layer: every imported geometry stores source/provider, source object ID, capture timestamp, CRS, resolution/accuracy metadata and raw-reference URI.

7. Recommended relational rules

Cities.CityName should not be the sole unique key; use CityId and optionally a country/state composite uniqueness rule.

CityStructures has one stable CityStructureId that never changes when the source provider changes.

StructureGeometryVersions separates the immutable Original baseline from Updated versions. Never overwrite Original coordinates.

StructureVertices is versioned through GeometryVersionId, so the same CityStructureId can have multiple vertex snapshots.

VertexSequence preserves polygon order. For a closed footprint, the first and final coordinate may be the same geometrically, but the logical vertex count should not double-count the closing point.

NumberOfEdges and NumberOfVertices are derived from normalized geometry and stored for fast display; a nightly integrity job can recalculate them.

Use a unique constraint on (CityStructureId, GeometryVersionId, VertexSequence).

Use a unique constraint on (CityStructureId, StructureExternalId, Provider) where provider identity is available.

Store both WGS84 geographic coordinates and a metric projected representation when precise distance comparison is required.

8. Vertex coordinate model

To remove ambiguity from the original requirement, define X/Y as horizontal coordinates and Z as elevation. For WGS84, X=longitude and Y=latitude. For metric calculations, transform to a suitable projected CRS and use easting/northing as X/Y. TopX/TopY/TopZ describe the upper observable point associated with a vertex when a 3D source exists; BottomX/BottomY/BottomZ describe the base/ground point. For ordinary 2D building footprints, Top and Bottom horizontal coordinates may be identical and only Z differs or is unavailable.

10. Background daemon / scheduled comparison

Create a separate .NET Worker Service project, for example: StructureWatch.GeometryDaemon.

Load active cities whose scheduled job is due.

For each city, load structures above the configured height threshold.

For each structure, load Original baseline and the latest Updated geometry version.

Verify geometry hashes, vertex count, sequence and CRS before comparison.

Transform both geometries into the same metric CRS.

Match vertices by stable vertex sequence plus geometry-nearest matching when a source changes the polygon node count.

Calculate ΔX, ΔY, horizontal distance and, where available, ΔZ/3D distance.

Compare each delta against configured thresholds and source uncertainty.

Create StructureChangeEvents only when the difference is material relative to the stated source accuracy.

Create/refresh ValidationCases for material changes or low-confidence results.

Write IngestionRuns and AuditEvents.

Expose job health to the MVC application.

11. Change-detection formula

For metric coordinates:

ΔX = X_updated − X_original

ΔY = Y_updated − Y_original

HorizontalDelta = sqrt(ΔX² + ΔY²)

ΔZ = Z_updated − Z_original (when both Z values are valid)

Total3DDelta = sqrt(ΔX² + ΔY² + ΔZ²)

Recommended decision logic: alert only when measured movement exceeds both the configured movement threshold and the combined uncertainty budget. Otherwise classify the result as 'Within Source Uncertainty' and retain it for trend analysis.

15. Example comparison SQL concept

A production implementation should calculate differences in a metric CRS rather than subtracting latitude/longitude degrees directly. Conceptually, query Original and Updated vertices by CityStructureId + VertexSequence, transform to a common projected CRS, calculate deltas, then insert only qualifying differences into StructureChangeEvents.

Recommended report columns: CityName, CityStructureId, StructureName, VertexSequence, OriginalX, OriginalY, UpdatedX, UpdatedY, DeltaXmm, DeltaYmm, HorizontalDeltaMm, OriginalCapturedUtc, UpdatedCapturedUtc, SourceAccuracyM, ConfidenceScore, Classification.

16. Integrity and validation rules

Reject self-intersecting or invalid building polygons unless explicitly marked as source geometry requiring repair.

Require at least 3 distinct horizontal vertices for a polygon footprint.

Validate that vertex sequence is ordered and edges connect sequential vertices.

Check that stored NumberOfEdges and NumberOfVertices agree with normalized geometry.

Reject impossible coordinates and mismatched CRS metadata.

Keep source capture date with every geometry version.

Do not compare geometries from different CRSs without transformation.

Do not label a change as structural movement when it may be imagery parallax, map revision, geocoding drift, polygon remapping or source-resolution error.

Keep the original baseline immutable and record all baseline replacements as an explicit reviewed version transition.

Use authentication/authorization roles for Administrator, Data Operator, Reviewer and ReadOnly.

Rate-limit external provider calls and cache source responses according to provider terms.

Use structured logs with run ID, city ID, structure ID, provider and correlation ID.

Alert on repeated provider failures, stale source data and daemon inactivity.

StructureWatch Guard – Building Structure Geometry & Change Monitoring Design

Enhanced Section — Subsurface Geology, Foundation Bed & Underground Change Monitoring

1. Purpose and Scope

Extend StructureWatch from above-ground structure geometry and SAR/InSAR deformation monitoring into a vertical digital-twin model that represents the subsurface beneath each monitored structure. The module shall use the existing StructureVertexId as a common spatial reference while preserving the distinction between directly observed geology, borehole/geotechnical observations, geophysical interpretation, regional geological mapping, and inferred/interpolated surfaces.

Capture soil, fill, loose layers, dense layers, weathered rock, competent/bedrock layers, foundation depth and groundwater observations.

Associate subsurface observations with existing structure vertices and nearby boreholes without falsely treating an offset borehole as an exact vertex measurement.

Maintain immutable baseline and versioned current subsurface models.

Compare layer boundaries, thickness, bedrock depth, groundwater observations and model revisions over time.

Animate historical underground conditions in the same 3D scene as the structure, foundation, vertices and surface deformation.

Provide provenance, uncertainty, confidence and observed-versus-inferred status for every underground observation.

2. Core Analytical Requirements

A structure may have multiple subsurface profiles; geology shall not be assumed uniform beneath all vertices.

Each StructureVertexId may act as a vertical reference axis, but each layer boundary must retain its own measured or inferred depth/elevation.

All elevations shall record the applicable vertical datum; all horizontal coordinates shall record the CRS.

Depth and elevation shall be stored in meters internally, with UI conversion to mm/cm/feet/inches as required.

The system shall distinguish physical change from improved geological knowledge. A new borehole or revised geological map shall not automatically be classified as physical underground movement.

Interpolated geological surfaces shall be explicitly labeled as interpolated/inferred and shall retain the source observations used to construct them.

No underground layer shall be invented when supporting observations are unavailable; the system shall represent the condition as UNKNOWN.

Engineering conclusions such as foundation failure, unsafe bearing capacity or causation shall not be automatically inferred from geological change alone.

The existing City → CityStructure → GeometryVersion → StructureVertex model becomes the common spatial spine for the above-ground and below-ground digital twin.

10. Operational Workflow

Load active CityStructures and their current StructureGeometryVersion.

Use StructureVertices to construct structure-specific subsurface reference axes and area of interest.

Discover regional geology, boreholes, geotechnical records, geophysical products and groundwater observations.

Normalize coordinates, horizontal CRS and vertical datum.

Import direct observations first; retain source identifiers and accuracy.

Associate nearby boreholes to structure vertices using distance/bearing rather than silently treating them as exact vertex measurements.

Build versioned geological layer profiles.

Generate bedrock and layer-boundary surfaces only where sufficient observations exist; label interpolated regions.

Compare the new model to the previous approved model.

Classify differences as physical change, data refinement, source conflict, new observation, interpolation change or unknown.

Create SubsurfaceChangeEvents and ValidationCases where review is warranted.

Expose the underground model and historical versions to the 3D UI.

11. 3D UI and Animation Requirements

Use the same StructureVertexId values to render vertical reference columns from the structure surface down through the subsurface.

Display building, foundation, soil/loose layers, dense layers, weathered rock, competent rock, bedrock and groundwater as independently toggleable layers.

Allow rotate, pan, zoom, depth slicing and vertical exaggeration.

Display vertical exaggeration explicitly, e.g. 5×, so users do not mistake visualization scaling for actual geology.

Provide a timeline slider that changes the active subsurface geometry/model version.

Animate layer boundaries, bedrock surfaces, groundwater observations and detected changes.

Show observation points/boreholes and their actual offsets from vertices.

Use different visual treatment for observed versus inferred/interpolated surfaces.

Synchronize the underground scene with the existing surface satellite/SAR deformation timeline.

14. Data Quality and Safety Constraints

Regional geological maps are contextual data and shall not be represented as building-specific measured depth profiles.

A new geological interpretation shall not be interpreted as physical movement unless independent evidence supports that conclusion.

All measurements must retain uncertainty and source quality.

No alert shall be generated solely because an inferred/interpolated boundary changed.

Borehole observations shall preserve their actual location and investigation depth.

Conflicting sources shall be retained rather than silently overwritten.

Original/authoritative records shall be immutable; corrections create a new version with provenance.

Engineering validation remains necessary for decisions involving foundation capacity, structural safety or suspected subsidence.

16. Acceptance Criteria

A monitored structure can display its original/current surface geometry and corresponding underground model in one 3D scene.

Every subsurface observation is traceable to a source and observation method.

The same StructureVertexId can be used to inspect the surface point and its underground reference profile.

Nearby boreholes can be associated to vertices with explicit distance/bearing.

Layer top/bottom depth and elevation can be compared between model versions.

Bedrock depth can be displayed and animated across historical observations.

Groundwater observations can be displayed as a time series and spatial layer.

The system distinguishes physical change from model refinement/new information.

Interpolated geological surfaces are visibly identified as inferred.

Surface SAR/InSAR displacement and underground changes can be viewed together without automatically asserting causation.

The daemon can ingest, version, compare and audit subsurface data using the same operational framework as surface monitoring.

17. Consolidated StructureWatch Digital-Twin Model

The enhanced architecture creates a vertical digital twin: Cities → Structures → Surface Geometry/Vertices → Foundation → Subsurface Profiles → Geological Layers → Bedrock → Groundwater, with Satellite/InSAR deformation and subsurface change events feeding a common validation workflow. StructureVertexId is the common spatial reference, while version IDs, source IDs, uncertainty and observation methods preserve the scientific distinction between measured, modeled and inferred information.
